# ADR-014: 再帰の深さの限界は、今は直さない

## ステータス

採択済み（2026-11-04）。深い再帰を扱う必要が出たら見直す。

## コンテキスト

JSVisualizer の連載の下書きで、`function s(n) { ... return n + s(n - 1); }` の `s(100)` は動くのに `s(500)` はスタックオーバーフローで止まることがわかった。この限界はインタプリタの仕様なのか、実行環境の限界なのかを調べた。

インタプリタに深さの上限の設定はない。エラーはホストの JS エンジンが投げる `RangeError: Maximum call stack size exceeded` で、`ExecutionError` がメッセージをそろえている。

Node.js 22 で測った結果:

| 項目 | 結果 |
|------|------|
| 止まる深さ（既定のスタック） | ゲストの呼び出しで約 150〜210 段。同じプログラムでも実行ごとに 149〜211 段で変わる（最適化の進み具合の影響と考えられる） |
| スタックサイズを 2 倍・4 倍にしたとき | 成功した最大の深さが 187 → 374 → 749 と比例して増える |
| ゲストの呼び出し 1 回あたりのホストのフレーム | 約 17 個（`s(n)` の場合。文や式の入れ子で変わる） |
| 同じ環境の普通の JS の再帰 | 約 9,900 段 |

限界が浅いのは、評価器が AST を再帰でたどるため。AST の 1 段ごとに `evaluate` → `Recorder.record` → クロージャ → `_eval` の 4 フレームを使う。`_eval` は大きな switch を持つ関数で、1 フレームも大きいと考えられる（1 フレームの大きさは未計測）。

ブラウザごとの違いは未計測。

## 決定

今は直さない。限界はホストのスタックの大きさで決まるものとして、既知の制限に書く。

## 結果

- 教材の再帰（階乗、fibonacci、マージソートなど）は浅いので問題にならない
- `power(2, 1000)` のように深さが数百を超える再帰は、正しいプログラムでも止まる。エラーの文面は「再帰が止まっていない可能性があります」としている
- 止まる深さは実行ごとに変わるので、深さに依存するテストを書かない（JSVisualizer で、止まる位置に依存したテストが手元の Node 22 では通り、CI の Node 24 で失敗したことがある）
- 実行の記録はイベントごとに呼び出し元のフレームも保存するので、スタックを大きくしてもメモリの負担が増える。`--stack-size` を 4 倍にしてヒープが足りなくなったことがある

## 代替案

見直すときの候補:

- 評価器を再帰を使わない形（明示的なスタックやジェネレータ）に書き直す: 限界をほぼなくせて、上限を自分で決められる。作業は大きい
- 評価 1 回あたりのフレームを減らす（`evaluate`・`record`・クロージャをまとめる）: 作業は小さい。効果は 2 倍程度と見込むが未計測
