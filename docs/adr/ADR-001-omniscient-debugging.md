# ADR-001: オムニシエントデバッグ方式と4操作ステップAPI

- **決定日**: 2026-05-23
- **作成日**: 2026-08-10（セッションログから事後的に作成）
- **ステータス**: 承認済み

## 背景・課題

プロジェクト開始時点（コード0行）で、ステップ実行（ステップイン・ステップ
オーバー・ステップアウト・ステップバック）のAPIを備えたJavaScriptインター
プリターを実装することになった。「どうやってステップを管理するか」の
基本方針を最初に決める必要があった。

## 決定の経緯

1. Claudeが用途を確認（対話型デバッガーかプログラム的APIか）→「両方」と回答。
2. **Claudeの最初のプラン**: ジェネレーターベース評価器。各文の境界で
   `yield`し、任意のタイミングで一時停止・再開する方式。ステップバックは
   「毎回最初から再実行するリプレイ方式」で対応する計画だった。
3. **開発者がこのプランを却下**（ExitPlanModeの提示を拒否。コードは
   まだ1行も書かれていない段階）。
4. 開発者が自身の考える方式を詳細に提示: 「ステップ実行の方式を次のように
   考えています．まず，プログラムをステップ実行する．各ステップの状態を
   すべて記憶する．ステップ実行では，ステップイン，ステップオーバー，
   ステップアウト，ステップバックの種類に応じて，適切な状態を呼び出す．
   この実装は妥当でしょうか？」——「オムニシエント」という語は使っていない。
5. Claudeが応答: 「非常に良い設計案です。この方式は**オムニシェント・
   デバッグ（全知型デバッグ）**と呼ばれる手法に相当します」。自案
   （ジェネレーター＋リプレイ）を撤回し、開発者の案（スナップショット
   配列）を採用した。

## 決定

`JSDebugger`のコンストラクタでプログラムを末尾まで実行し、全ノードの
`TraceEvent`を`trace`配列に記録する（オムニシエントデバッグ）。ステップ
操作は配列`cursor`の操作に還元される。

```js
this.trace = [ state0, state1, state2, ... ];
this.cursor = 0;

stepIn()   → this.cursor++            // O(1)
stepBack() → this.cursor--            // O(1)
stepOver() → callDepth で判定してジャンプ
stepOut()  → 同上
```

## 根拠

- `stepBack`がO(1)で実現できる（配列を1つ戻すだけ）。ジェネレーター＋
  リプレイ方式では毎回最初から再実行が必要で、この点が最大の弱点だった。
- 任意ステップへの直接ジャンプが可能（対話型UIでのスライダー操作等に有利）。
- 実装がシンプル（ステップ操作の本体が「配列インデックス操作」のみになる）。

## トレードオフ

- プログラムが終了しないと記録できない（無限ループ対策として`maxSteps`の
  上限を設ける）。
- 状態数 × 1状態のサイズ分のメモリが必要。
