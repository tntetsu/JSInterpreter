# ADR-013: 呼び出し元のフレームに、呼び出した地点から見える変数を記録する

- **決定日**: 2026-11-04
- **作成日**: 2026-11-04
- **ステータス**: 承認済み

## 背景・課題

利用側の JSVisualizer のコールスタックビューで、関数の実行中に呼び出し元のフレームから `let`／`const` の変数が消えていた。

`TraceEvent.frameEnvs`（ADR-006）は、各フレームの `callEnv` のスナップショットだった。関数本体は `callEnv` の内側に作られるブロックの環境で評価されるので、記録されるのは引数と `var` だけで、関数本体やブロック（`for` の本体など）の `let`／`const` は含まれなかった。グローバルの `for` の中から関数を呼んだときも、そのブロックの変数は `env` のチェーンに含まれないので記録されなかった。

また、`env` と `frameEnvs` を別々に複製していたので、同じ配列を指す変数がスナップショットの上では別の物になっていた。

## 決定

- `Recorder` が、いま評価しているノードの環境（`curEnv`）と、各フレームを呼び出した地点の環境（`callSiteEnvs`）を覚える。フレームの出入りは `pushFrame()`／`popFrame()` で行う
- `frameEnvs[i]` は、次のフレームを呼び出した地点（最も内側のフレームはいま評価している環境）から `callEnv` までの変数をまとめたものにする（`Environment.snapshotFrom()`。内側の同名の変数を優先）
- `TraceEvent.globalBlockVars` を追加する。最初のフレームを呼び出した地点からグローバルスコープの手前までの変数をまとめたもの（`Environment.snapshotBlocks()`）。関数の外では空
- 1 つの TraceEvent の `env`・`frameEnvs`・`globalBlockVars` で複製の対応表 `seen` を共有する（`Recorder.snapshotVars()`）。同じ配列やオブジェクトを指す変数は同じ複製を指す

## 結果

- 呼び出し元のフレームの変数が、呼び出しの最中も現在の値で見える
- 呼び出し元と呼び出し先が同じ配列を共有していることが、スナップショットの同一性でわかる
- 記録する変数が増えるので、再帰の深いコードの記録は 3 割ほど重くなる（4 万 8 千ステップで 650ms → 860ms）

## 検討した代替案

- 関数本体のブロックの環境だけを追加する: ループの中から呼んだときの症状が残るので不採用
- 関数本体を `callEnv` で直接評価する: `function f(x) { let x; }` の扱いなど言語の動作に影響するので不採用
